Artifact 功能调查报告

生成时间：2026-07-04　·　范围：Makro 桌面后端 cmd/gui/artifact_service.go + iOS ArtifactsView/ArtifactPreviewView　· 报告本身存于 ~/Desktop/Code/Makro/artifacts/（属于 dev session 的扫描目录，可作为 artifact 被发现）
TL;DR — 根因

Artifact 功能本身实现正确、权限/访问控制正常、iOS 端调用也没问题，但它几乎永远扫不到任何文件： 后端只在每个 session 工作目录下的 dist / output / artifacts / public / build 这 5 个子目录里找 .html/.mp4/.webm/.mov；而实际上 coding agent（Claude Code 等）把生成的 HTML 直接写到了项目根目录（session cwd 顶层）。这 5 个扫描目录在你的 10 个 session 里一个都不存在， 所以接口始终返回空。例如 audit session 的目录下明明有 8 个 .html， /api/artifacts?session=audit 却返回 null。

① 功能实现 & 存储路径

实现文件cmd/gui/artifact_service.go（后端）+ server.go 两个 HTTP handler 存储方式没有中央 artifact 目录。Artifact 不是"被存到某处"，而是被发现于每个 tmux session 的当前工作目录下。 session cwd 解析tmux display-message -t <session> -p #{pane_current_path}（与 agent 无关，读 tmux 状态） 扫描目录dist, output, artifacts, public, build 识别类型.html/.htm → html；.mp4/.webm/.mov → video（其余一律忽略） HTTP 接口 GET /api/artifacts?session=X → JSON 列表（newest first）
GET /api/artifact?session=X&path=Y → 文件内容，http.ServeContent 提供视频 Range/seek 路径安全ResolveArtifact 用 filepath.EvalSymlinks + isWithinCwd 防 ../符号链接逃逸 → 安全
关键点：所谓"artifact 目录"不是固定路径，而是 <session-cwd>/{dist,output,artifacts,public,build}。 没有 session cwd = 没有 artifact。文件必须落在那 5 个子目录里才会被列出。

② iPhone 是否正确使用 + 文件是否真的生成 核心问题在这

iPhone 端使用 — 正确

  • ArtifactsView：选 session → fetchArtifacts(session:) → 按 html/video 分组 → 点击进 ArtifactPreviewView。逻辑无误。
  • ArtifactPreviewView：不直接用远程 URL 喂 WKWebView/AVPlayer（自签证书过不了校验），而是经 APIClient.fetchArtifactContent（带 TLS pinning）下载内容 → HTML 用 loadHTMLString 本地渲染，视频写临时文件给 AVPlayer。设计正确，规避了证书问题。
  • URL 构造：/api/artifacts?session= 与 /api/artifact?session=&path=，与后端一致。

文件是否真的生成到 artifact 目录 — 没有（这才是病根）

实盘扫描 10 个 session，没有一个在 dist/output/artifacts/public/build 里有 html/video：

根因：agent 把 HTML 写到了 session cwd 顶层（例：~/Desktop/Code/agent-memory-overview.html、social-insurance-calculator.html、memory-storyboard.html …）， 而后端只扫 cwd/{dist,output,artifacts,public,build}。这 5 个目录全部不存在。 → ListArtifacts 返回空 → iOS 永远显示 "No artifacts found"。

实测：curl /api/artifacts?session=audit → null，而该目录下确有 8 个 .html。

附带小 bug：无结果时 ListArtifacts 返回 null（var entries []ArtifactEntry 未赋值），而非 []。 注释里写"返回空 slice（非 nil）"但代码没做到。Swift JSONDecoder 多数情况能容错，但前端/其他客户端可能踩坑。建议返回 []。

③ 手机端访问 & 路径配置

  • 访问链路：iPhone → HTTPS → /api/artifacts（列表）//api/artifact（内容）→ 后端读 session cwd 下文件。链路本身正确。
  • 路径配置：iOS 的 Config.httpBaseURL 指向后端；artifact 路径用相对 session cwd 的 path（如 dist/index.html），由后端解析。无路径配置错误。
  • 证书：自签 TLS。列表/内容走 APIClient（有 pinning）→ OK；预览刻意不走远程 URL 以避开 WKWebView 证书问题 → OK。
  • 结论：手机端访问与路径配置没有问题。它"看不到 artifact"是因为上游接口返回空（见 ②），不是手机的问题。

④ 权限 & 访问控制

  • HTTP 鉴权：/api/artifacts 与 /api/artifact 都在 /api/ 下，被 authMiddleware 保护，要求 Authorization: Bearer <password>，且用 subtle.ConstantTimeCompare 常量时间比较（防时序侧信道）。鉴权正常。
  • 路径穿越：ResolveArtifact 做了符号链接解析 + cwd 边界检查，../绝对路径/软链逃逸都会被拒。安全。
  • 文件系统权限：artifact 文件都是当前用户所有、可读（实测 find 能列出）。无权限问题。
  • 结论：权限与访问控制无问题。

解决方案

方案 A（推荐）：同时扫描 session cwd 顶层

在 ListArtifacts 里，除了现有的 5 个子目录递归扫描，再扫 cwd 顶层（maxdepth=1）的 html/video。这正好匹配 agent 实际的写盘行为。

// cmd/gui/artifact_service.go — ListArtifacts 内，在扫描子目录的循环之前/之后加：
// 顶层（depth 1）的 html/video —— agent 实际写入的位置
topEntries, _ := os.ReadDir(cwd)
for _, e := range topEntries {
    if e.IsDir() { continue }
    if t := artifactExtType(e.Name()); t != "" {
        if info, err := e.Info(); err == nil {
            entries = append(entries, ArtifactEntry{
                Name: e.Name(), Path: e.Name(), Type: t,
                Mtime: info.ModTime().Unix(), Size: info.Size(),
            })
        }
    }
}

顶层只取 depth=1，不递归 → 不会把 node_modules/.git 里的噪声带出来；项目根的 .html 基本都是 agent 有意生成的产物。

方案 B：扩大扫描目录集合 / 加深递归

往 artifactScanDirs 加更多约定目录（如 www、site、out），或允许项目通过 .makro 配置自定义扫描目录。比 A 更"守规矩"，但解决不了"文件在根目录"这个最常见情况。

方案 C：约定 agent 写到固定目录

在系统提示里要求 agent 把产物写到 ./artifacts/。最干净，但依赖 agent 遵守，迁移成本高。

建议：直接上 方案 A（最小改动、立刻见效），再叠加 方案 B 的可配置扫描目录作为增强。

顺手修的小问题

  • ListArtifacts 无结果时返回 []ArtifactEntry{} 而非 nil，使 JSON 为 []（与注释一致，避免 null 歧义）。
